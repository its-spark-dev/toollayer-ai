# v0.2.2 — Read-your-own-write correctness

A patch release fixing when the Control Plane commits.

**A successful mutating response now means the transaction has committed before the response
is sent.** Previously it could mean "will commit shortly", and a client that immediately read
back what it had just written could be told the write did not exist.

**Migration impact: none.** No API shape, status code, error code, configuration key, contract
document or accepted input changed. The contract version stays at 1.1.0.

## The defect

FastAPI runs the exit half of a `yield` dependency *after* the response has already gone to
the client. The Control Plane's request-scoped session committed there. So the caller received
a `201`, and the row it described became durable afterwards.

Two instances reached CI, both passing on re-run:

- `POST /admin/v1/deployments` returned `201`, and the immediately following request for that
  deployment returned `404 no deployment exists with that key`.
- `PATCH /admin/v1/connectors/{key}/draft` returned a revision, and the immediately following
  publish rejected that same revision as a `revision_conflict`.

Different endpoints, one cause.

## Why it was hard to see

On a **reused keep-alive connection** the defect is invisible. The server finishes the entire
request cycle — dependency teardown included — before it reads the next request off that
socket, so the two requests serialize and the follow-up always observes the write.

Send the follow-up on a **different connection** and it is handled independently, and can begin
while the previous request's commit is still pending.

That distinction is the whole finding, and it is what the measurement shows. Real server, real
socket, real database file, identical code, only the connection shape varied:

| Mode | create → read pairs | Violations |
|---|---|---|
| keep-alive, sequential | 1500 | **0** |
| keep-alive, 16 concurrent | 1500 | **0** |
| fresh connection, sequential | 1500 | **5** |
| fresh connection, 16 concurrent | 1500 | **2** |

It also explains the shape of the CI failures. A run under load is more likely to let a pooled
connection lapse between steps, and the next request then opens a fresh one — so the failure
appears occasionally, on a loaded machine, and never on a re-run.

Investigated and ruled out along the way: multiple server workers, stale write-ahead-log files,
isolation between pooled database connections, concurrency inside the demo script, health-check
and readiness ordering, and client-side retries. Twenty-five consecutive local demo runs passed,
which is why the connection-shape experiment was the one that mattered.

## The fix

Mutating routes commit after the endpoint returns and **before the response is built**. It is
applied through a route class on both routers, so it holds for every route rather than each one
remembering, and the session scope's own commit remains as a fallback.

This is a change to *when* the commit happens. It is not a retry, and it is not specific to any
one database backend — the ordering was wrong regardless of what sits underneath.

A second consequence: because the commit now happens while the response is still being
assembled, a commit that *fails* produces a `500` instead of being logged after a `201` the
client has already accepted.

Verified: **zero violations across 24,480 requests** over four full stress passes.

## Tests

`tests/integration/test_read_your_own_write.py` — four tests against a real server on a real
socket with a real database file, because the defect lives in connection and event-loop
scheduling that an in-process test client does not model.

- **The deterministic guard**: the session must not still be in a transaction when the
  dependency tears down. This fails **100%** of the time without the fix.
- Create → immediate read on a fresh connection, 150 iterations.
- Reviewed draft → publish on a fresh connection, 25 iterations.
- 150 concurrent independent clients across 12 workers.

Confirmed to fail with the fix removed and to pass with it restored. The deterministic guard is
the real regression protection; the end-to-end sequences reproduce the reported symptom on the
connection shape that exposes it.

## Also

The end-to-end demo job now prints each service's log inline when it fails, in addition to
uploading it. An uploaded artifact does not survive a job re-run, and re-running is the first
thing anyone does with an intermittent failure — which is how the evidence for this one was
lost while it was being investigated.

## Remaining limitations

Unchanged from v0.2.1: static admin and service tokens; caller identity asserted rather than
verified in the default demo topology; no external identity-provider integration; no TLS or
mTLS in the local Compose topology; no secret manager; polling-based revocation; a DNS
time-of-check-to-time-of-use gap with no pinned-IP protection claimed; no rate limiting; a
mutable rather than tamper-evident audit trail; no metrics or tracing; single-tenant; no OAuth
credential broker; one tool per request; no hosted model provider.

Two consistency notes specific to this release:

- The guarantee established here is **read-your-own-write for a client that observes a success
  response**. It is not serializability, and concurrent writers to the same resource still rely
  on the existing optimistic revision checks.
- The fallback commit in the session scope still runs during dependency teardown. It is a
  no-op in the normal path and exists so that a route added outside the route class is not
  silently uncommitted, rather than as a second mechanism.

This is a portfolio project, not a production system.
