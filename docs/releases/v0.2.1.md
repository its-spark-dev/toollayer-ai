# v0.2.1 — YAML ingestion hardening

A patch release. It fixes three defects at the ingestion boundary, two of which turned a small
authenticated upload into an HTTP 500.

**Migration impact: none.** The set of documents this ingester accepts is unchanged, the
contract version stays at 1.1.0, and no configuration or artifact change is required.

## What prompted it

A CodeQL alert — `py/unsafe-deserialization`, reported Critical — on
`yaml.load(text, Loader=_NoDuplicateKeyLoader)`.

**The alert was a false positive.** Unsafe object deserialization was not possible, and there
was no code execution path. Established by inspection and by test rather than by the base class
looking reassuring:

| Property | Finding |
|---|---|
| Loader MRO | `SafeLoader` and `SafeConstructor` only — no `Loader`, `FullLoader`, `UnsafeLoader`, `Constructor`, `FullConstructor` or `UnsafeConstructor` |
| Constructor table vs `SafeLoader` | nothing added, nothing removed, exactly one entry replaced: the standard mapping tag |
| `python/*` constructors | none |
| Multi-constructors | none — and these match by tag *prefix*, which is how `!!python/object:` is actually reached |
| Python-tag payloads | every one refused, with a sentinel confirming no callable was ever constructed |

CodeQL resolves the `Loader=` argument against a list of known-safe loader classes. A
`SafeLoader` subclass defined in this repository is not on that list, so the call was flagged.
The query behaved correctly given what it can prove.

Investigating it is what found the real problems.

## Fixed

**1 · Deeply nested documents crashed the request.** PyYAML's scanner and parser are iterative;
its **composer is not**. A document nested past CPython's stack limit raised `RecursionError`
from inside the library before reaching the depth check in `_enforce_shape` — the code path
whose comment promises exactly that cannot happen. **692 bytes was enough**, and an 830-byte
upload to `POST /admin/v1/connectors` returned `500 internal_error`. Now refused as
`document_too_large` at every depth tested, up to 200 000.

**2 · A non-scalar mapping key crashed the request.** `? {a: 1}` is valid YAML and
unrepresentable in JSON. It reached a hashability check with an unhashable value and raised an
unhandled `TypeError`, also a 500. Now `invalid_source_document`.

**3 · Merge keys were mislabelled.** `<<: *anchor` was reported as "not well-formed YAML",
which is untrue — it is well-formed and deliberately unsupported, because resolving one gives
the reviewed document and the file on disk different key sets. Now refused as itself, and
listed with the other ingestion refusals in `docs/control-plane.md`.

## Changed

The loader is instantiated directly and `get_single_data()` called on it, rather than going
through `yaml.load(..., Loader=...)`. That generic call takes its safety from an argument
defined somewhere else, and every unsafe use of PyYAML looks exactly like a safe one until you
follow it; removing the argument leaves the loader class named at the one place it is used.

`_assert_loader_is_safe()` now runs at import and refuses to start a build whose loader has
gained an unsafe base class, a `python/*` tag, or a multi-constructor — the three ways a
`SafeLoader` subclass gets widened without any line that looks security-relevant changing.

## Tests

**42 new**, in `tests/security/test_yaml_ingestion_safety.py`: the loader's tag surface, each
way the subclass could be widened silently, every structural refusal, the parser limits, and
the absence of the `yaml.load` call asserted at syntax level.

No payload is permitted a side effect. A sentinel records any callable construction, and
`os.system`, `os.popen` and the `subprocess` entry points are trapped to fail the test if a
parse ever reaches them. The payloads are also proven live: each tag is checked against
`yaml.UnsafeLoader`'s constructor table, establishing they are tags a permissive loader would
act on — without any of them being acted on.

## Compatibility

Anchors, aliases and every standard scalar type still load, and the repository's own example
specification is asserted to parse unchanged. Duplicate-key rejection is unchanged. What
changed is that three inputs which previously produced an HTTP 500 or a misleading message now
produce the project's structured errors.

## Remaining limitations

Unchanged from v0.2.0, and stated rather than implied: static admin and service tokens; caller
identity asserted rather than verified in the default demo topology; no external
identity-provider integration; no TLS or mTLS in the local Compose topology; no secret manager;
polling-based revocation; a DNS time-of-check-to-time-of-use gap with no pinned-IP protection
claimed; no rate limiting; a mutable rather than tamper-evident audit trail; no metrics or
tracing; single-tenant; no OAuth credential broker; one tool per request; no hosted model
provider.

Two parser limitations are worth naming specifically, both unchanged by this release:

- **Nesting is bounded by refusal, not by cheap pre-screening.** A document too deep for the
  composer is now refused correctly, but the refusal happens when the recursion limit is hit
  rather than before parsing begins. Enforcing the limit on PyYAML's iterative event stream
  first would be stricter; it also costs roughly 76% more parse time on legitimate documents,
  which was not worth paying for an outcome the caller cannot distinguish.
- **Alias expansion is bounded by the node limit, not by the parser.** PyYAML shares aliased
  objects rather than copying them, so the billion-laughs shape costs O(source) to construct
  and is caught by the node-count walk in 0.02 s. That is a property of PyYAML's construction
  strategy that this project depends on rather than enforces.

This is a portfolio project, not a production system.
