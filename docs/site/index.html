ToolLayer AI

Build once. Orchestrate anywhere.

An AI application becomes useful when it can call real APIs — and dangerous at the same moment. ToolLayer AI turns an OpenAPI document into a reviewed, versioned, signed artifact, and gives a runtime the machinery to execute only that, under policy.

The problem, and the shape of the answer

One paragraph each.

Problem

Deriving a model's tool list from an API specification at startup leaves you with no artifact: nothing to review, version, verify, or roll back. And the component choosing the call is a language model, which produces plausible output rather than correct output.

Solution

A Control Plane converts, reviews and publishes immutable connector versions and deployment snapshots. A reference Runtime consumes one snapshot and executes at most one governed tool call per request — validated, authorized, and sent only to an allowlisted destination.

One OpenAPI operation in, one governed tool out

Deterministic: the same document always produces the same tools, which is what makes the published digest mean anything.

Architecture

Two services that never import each other. They share one contract package and communicate through a single read-only endpoint. 

  OpenAPI document
        │
        ▼
  ┌─────────────────────────── Tool Control Plane ───────────────────────────┐
  │  convert  →  review  →  publish (immutable version)  →  snapshot         │
  │             (a human decides what becomes callable, and by whom)         │
  └──────────────────────────────────┬──────────────────────────────────────┘
                                     │  signed, digest-addressed snapshot
                                     │  GET /internal/v1/…/snapshot  (ETag, 304)
                                     ▼
  ┌────────────────────── LLM Orchestration Runtime ─────────────────────────┐
  │  discover → select → generate args → validate → authorize → execute      │
  │             (one snapshot revision for the whole request)                │
  └──────────────────────────────────┬──────────────────────────────────────┘
                                     │  allowlisted origin, streamed and bounded,
                                     │  no redirects, no proxies, no retries
                                     ▼
                              Upstream HTTP API

The security boundary that matters most

The arguments come from a language model. The destination comes from a stored artifact. Neither is trusted.

Default-deny destinations

Exact origin matching, no wildcard, and every resolved address checked after DNS — so a public name pointing at 169.254.169.254 is refused. Redirects are a failure, not a hop.

Closed schemas, binding-driven requests

Arguments are validated against the published JSON Schema before anything is built, and the request is assembled from the tool's bindings rather than from the arguments. An undeclared field has nowhere to go.

Signed artifacts, not just hashed

The SHA-256 digest identifies content. An Ed25519 signature authenticates the producer, so an attacker who rewrites a snapshot and its digest still cannot make the runtime serve it.

No loop

A tool result is summarized and the turn ends. Nothing in an upstream response re-enters selection, so text inside a tool result cannot cause a second call.

Technology

What this is, and what it is not

This is a portfolio project, not a production system. The Control Plane is the product; the Runtime is a reference implementation that exists to prove the published artifact is usable and that the governance survives contact with model output.

Deliberately out of scope: real OAuth and end-user credential brokerage, multi-step tool chaining, conversation memory, a hosted model provider, multi-tenancy, and TLS termination. Caller identity in the demo topology is asserted by the host application rather than verified — a signed-token mode exists and the runtime reports which one is in force. Full dispositions are in feature parity and the threat model.
